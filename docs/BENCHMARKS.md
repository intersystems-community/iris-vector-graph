# Benchmarks

For application developers and IRIS operators deciding whether IVG is fast enough for a workload. Every number below
names the run that produced it: the date, the IVG code it ran (a release or a commit), the machine and the script.
Nothing on this page was measured for 4.6.0; it gathers the recorded runs, newest first. The full reports, with every
query, the method and what went wrong on the way, are for contributors in
[the benchmark report](dev/notes/ALT_VS_BASELINE.md) and its [catalog](dev/notes/alt-bench/CATALOG.md).

How to read them:

- **A laptop is not a server.** The laptop runs are a MacBook Pro (M3 Ultra) under other load (load average 8 to 31,
  noted per run); the AWS runs are a quiet `r7g` instance. The same code measured 1.21 against Neo4j on the laptop and
  1.00 on AWS a day apart, so compare a laptop number with a laptop number.
- **Older numbers measured older paths.** Since 4.3.0 most read-only Cypher runs in the native executor over `^KG`.
  A number from before 2026-10-22 measured the SQL path or an ObjectScript fast path that is no longer the default;
  those numbers are in [History](#history), dated, and not comparable with the rest.
- **Ratios are IVG's time divided by the other engine's**: below 1 IVG is faster. "At or ahead" counts queries at or
  under 1.1x.

## LDBC Social Network Benchmark against Neo4j and Memgraph

The LDBC SNB interactive and BI query shapes (IC, IS, BI and a few extra aggregates; 39 or 40 queries), on the full
SNB schema generated by the Spark datagen, one engine running at a time on the same data and parameter sets, every
engine capped at 900 s per query. Script: `scripts/bench/aws/run_sf10_compare.sh` (AWS) and the same runners locally;
each run's results stay on the machine that ran it, under the run name in the last column, not in the repository.

| Date       | IVG code                            | Machine            | Scale | IVG/Neo4j (at or ahead, within 3x) | IVG/Memgraph                      | Run                |
| ---------- | ----------------------------------- | ------------------ | ----- | ---------------------------------- | --------------------------------- | ------------------ |
| 2026-10-23 | `b239576`, compiled plans (4.4.0)   | AWS `r7g.4xlarge`  | SF1   | **0.76** (28 of 40, 37)            | **0.54** (3.14.0)                 | `aws-sf1-6`        |
| 2026-10-23 | `36e6b89`, compiled plans (4.4.0)   | AWS `r7g.8xlarge`  | SF10  | **0.90** (22 of 39, 32)            | 0.57 (3.14.0, `aws-sf10-3`'s run) | `aws-sf10-4`       |
| 2026-10-22 | `7110a5cf`, compiled plans (4.4.0)  | laptop, load 11-17 | SF1   | 1.01 (20 of 39, 36)                | 1.00 (3.9.0)                      | `local-sf1-257b`   |
| 2026-10-22 | `b80df559`, the 4.3.0 release       | AWS `r7g.4xlarge`  | SF1   | 1.00 (21 of 40, 35)                | 0.77 (3.14.0)                     | `aws-native-sf1-5` |
| 2026-10-22 | `338e6d5c`, native executor (4.3.0) | AWS `r7g.8xlarge`  | SF10  | 1.13 (18 of 39, 29)                | 0.73 (3.14.0)                     | `aws-sf10-3`       |

Neo4j is 5.24 Community in every run. In the newest SF1 run IVG is 3x or more ahead of Neo4j on BI08, BI16, BI05, BI17,
BI06, `BI_forum_members`, IC1 and IC6, and furthest behind on BI04 (3.8x), BI14 (3.8x), BI18 (3.2x) and IC3 (2.6x),
the grouped `count(DISTINCT)` and short ordered projections. BI11 (friend triangles) took IVG 80.3 s against Neo4j's
59.1 s and Memgraph's 54.4 s. Answers matched Neo4j's on every compared parameter set, except where an `ORDER BY`
leaves ties.

Loading SF10 (33.9 M nodes, 208.2 M edges, 2026-10-22, `aws-sf10-3`): IVG 13,994 s through its bulk loader, indexes
and adjacency index; Neo4j 7,394 s; Memgraph 5,897 s. SF1 (2026-10-23, `aws-sf1-6`): IVG 876 s, Neo4j 835 s,
Memgraph 605 s.

## DRKG traversals against Neo4j and Memgraph

The Drug Repurposing Knowledge Graph (97,238 entities, 5.87 M edges), from its largest hub
(`Anatomy::UBERON:0000473`), 3 warm-up and 20 timed runs, median. 2026-10-23, laptop (load average 20 to 31), IVG
`d9c8d367` (4.4.0 code), Neo4j 5.24.2, Memgraph 3.9.0; every engine's answer matched the counts computed from the
source file. Run `drkg-2026-10-24`.

| Query                                           | IVG    | Neo4j  | Memgraph |
| ----------------------------------------------- | ------ | ------ | -------- |
| `(s:Entity {id: $x})-[r]->(n) RETURN count(r)`  | 0.8 ms | 7.9 ms | 2.3 ms   |
| `-[*1..2]->(m) RETURN count(DISTINCT m)`        | 333 ms | 591 ms | 599 ms   |
| `-[*1..3]->(m) RETURN count(DISTINCT m)`        | 654 ms | 823 ms | 209.5 s  |
| `shortestPath((a)-[*..8]-(b)) RETURN length(p)` | 5.2 ms | 9.2 ms | 345 ms   |

Loading the whole of DRKG into IVG (2026-05-31, IVG 2.0.0, IRIS Community 2025.1, laptop, `scripts/load_drkg.py`
with `bulk_load_session`): 511 s for the edges at a steady 11.5 K edges/s, 50 s to rebuild the indexes, 550 s for
`sync()`; 1,115 s in all. The run, and what it found, is in [DRKG at scale](dev/notes/DRKG_SCALE.md).

## Graph algorithms

From 2026-05-28 to 2026-06-02, IVG 1.99.0 to 2.0.0, laptop, IRIS Community 2026.1 and Enterprise 2026.2.0AI;
synthetic Erdős-Rényi graphs (seed 42) and Zachary's karate club. Milliseconds. Details and the tiers behind each
number: [graph algorithms, June 2026](dev/notes/GRAPH_ALGORITHMS.md).

| Algorithm                         | Graph               | IVG                          | networkx    | Neo4j GDS | Measured, script                                 |
| --------------------------------- | ------------------- | ---------------------------- | ----------- | --------- | ------------------------------------------------ |
| Leiden, modularity (gamma 1.0)    | karate (34 n, 78 e) | 96 (end to end)              | 1 (Louvain) | 115       | 2026-05-28, `tests/perf/test_leiden_four_way.py` |
| Leiden, modularity                | ER(500, 2,437 e)    | 6                            | 24          | 206       | 2026-05-28, same                                 |
| Leiden, modularity                | ER(2000, 9,941 e)   | 60                           | 152         | 60        | 2026-05-28, same                                 |
| Closeness (harmonic), igraph tier | ER(500, 2,437 e)    | 19 (840 without igraph)      |             |           | 2026-06-02, Enterprise 2026.2.0AI                |
| Closeness (harmonic), igraph tier | ER(2000, 9,941 e)   | 119 (22,131 without igraph)  |             |           | 2026-06-02, same                                 |
| Betweenness, 200 sampled sources  | ER(2000, 5,936 e)   | 8 (Arno), 500 (ObjectScript) | ~8,000      |           | 2026-06-02                                       |

The Leiden times are end to end; IVG's quality equalled `leidenalg`'s (ARI 1.0) and Neo4j GDS's at ARI 0.898 on the
karate club. Which Arno build produced the Arno row is not recorded; the same notes say the build shipped then had no
betweenness function, so treat that row as unconfirmed. `betweenness_centrality(sample_size=0)`, the default, is the 200-source approximation, not an exact run.

Exact betweenness and harmonic closeness at larger sizes (October 2026, laptop, IRIS 2026.3.0AI enterprise, IVG on
the `alt-parity` branch of 4.2.3 with Arno loaded, Neo4j GDS 2.12.0, `scripts/bench/alt/algo_scale.py`): betweenness at 5,000, 10,000 and 20,000 nodes took IVG 30, 140 and 610 s against GDS's 2.25, 3.75
and 15.9 s; closeness 5.4, 21.7 and 86.5 s against 0.12, 0.20 and 0.71 s. IVG's whole-graph centralities are
interactive on graphs of a few thousand nodes, not tens of thousands.

A few hundred rows per call is the fast shape: a call is one transaction, and a transaction's cost per row grows with
its size. The chunk-size table and the reasoning are in the [Admin guide](ADMIN_GUIDE.md).

## Vector search

IVG compares vectors with IRIS's `VECTOR_COSINE`. `initialize_schema()` builds no approximate-nearest-neighbour index
on the default embedding table (`kg_NodeEmbeddings`), so `kg_KNN_VEC` there scans every row: its time grows with the
number of embeddings. A table for a `(graph, model)` route (`kg_emb_<hash>`) gets an HNSW index when it is created,
if IRIS accepts one, and records a refusal in `embedding_registry.index_error`. No IVG run on this page measures
either.

## Running a benchmark

Contributors reproduce these runs with the harness in `scripts/bench/` (`aws/` for the AWS runs, `alt/` for the
comparison report); [the catalog](dev/notes/alt-bench/CATALOG.md) lists every suite, what data it needs and how long
it takes. A comparison run should start from a freshly loaded namespace and `GraphSchema.tune_tables`: a namespace
loaded after its last `TUNE TABLE` planned one SNB statement 40 times slower.
