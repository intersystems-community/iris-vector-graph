# Migration Guide: v4.0.0

## TL;DR — this one changes the storage layout

4.0.0 makes an embedding a **graph-scoped, per-model** resource (spec 227). In
3.2.0 a vector was namespace-wide and graph-blind, so a KNN in a shared namespace
could return a neighbour belonging to another graph. Fixing that means moving
rows, not altering columns, and it breaks four things at once:

1. `Graph_KG.kg_NodeEmbeddings` and `kg_NodeEmbeddings_optimized` are re-keyed.
   The `id` column is **gone**.
2. `nodes` no longer declares `UNIQUE (node_id)`. A node ID may exist in more
   than one graph.
3. `rdf_labels` and `rdf_props` carry a `graph_id` and include it in their
   uniqueness.
4. `kg_KNN_VEC`'s fourth argument changed meaning while keeping its position and
   type. **A 3.2.0 caller still compiles.** See
   [The silent one](#the-silent-one-kg_knn_vecs-fourth-argument).

Spec 230 finishes the same job in three more places, and each one is breaking on
its own:

1. `Graph_KG.docs` is keyed `(graph_id, id)` and **`id` now means a node ID**. A
   document whose ID names no node is quarantined, not migrated. See
   [`docs` is keyed by graph](#docs-is-keyed-by-graph-and-id-is-a-node-id).
2. `Graph_KG.kg_EdgeEmbeddings` is keyed `(graph_id, s, p, o_id)` behind an
   identity primary key, and edge vectors route per `(graph_id, model_key)` like
   node vectors. See [Edge vectors](#edge-vectors-are-keyed-by-graph-and-routed).
3. `^KG("prop")`, `^KG("label")`, `^KG("deg2p")` and `^KG("deg2p_exact")` gain a
   **graph subscript**, matching `out`/`in`/`deg`/`degp` from spec 214. See
   [The `^KG` node stores](#the-kg-node-stores-gain-a-graph-subscript).

Run the whole upgrade before writing anything. One call performs all four steps in
the only order that works, and reports each separately:

```python
from iris_vector_graph.migrations import upgrade_to_4_0_0

report = upgrade_to_4_0_0(conn, dry_run=True)   # predict
report = upgrade_to_4_0_0(conn)                 # do it

for step in report.steps:
    print(step.name, "skipped" if step.skipped else step.report)
```

It is re-runnable. If it is killed, run it again: a step that has already produced
the 4.0.0 shape reports itself **skipped** rather than migrating migrated data, and
a step killed halfway is finished rather than declined.

Spec 227's embeddings pass is still callable on its own
(`migrate_to_graph_scoped_embeddings(conn)`), as are the three spec 230 steps
(`migrate_docs_and_edge_vectors`, `rekey_kg_node_stores`), for an install that has
already had one of them run against it by hand. `upgrade_to_4_0_0(conn,
steps=("docs", "edge_vectors"))` runs a named subset, in the same order.

## The silent one: `kg_KNN_VEC`'s fourth argument

In 3.2.0 the fourth parameter was `IN embeddingConfig VARCHAR(128)` — accepted
and ignored. In 4.0.0 it is `IN graphId VARCHAR(256)`, and it is load-bearing:

```sql
-- 3.2.0: the model name was ignored, the search was namespace-wide
CALL Graph_KG.kg_KNN_VEC(?, 10, NULL, 'all-MiniLM-L6-v2')

-- 4.0.0: still compiles. Now searches a graph *named* "all-MiniLM-L6-v2",
-- which does not exist, so it returns zero rows — no error.
```

The slot's position and type did not change, so there is nothing for IRIS to
reject and nothing for a deprecation warning to fire on. Audit every
four-argument `kg_KNN_VEC` call site before upgrading. Pass `''` (or `NULL`) for
the default graph.

`kg_RRF_FUSE` is the opposite case and fails loudly: it takes **seven**
parameters now, so a six-argument `CALL` is an arity error at runtime.
`Graph.KG.PyOps.HybridSearch` gained a trailing `graph As %String = ""` to match.

## Schema changes

### Embedding tables

```sql
-- 3.2.0
id VARCHAR(256) %EXACT PRIMARY KEY, emb VECTOR(DOUBLE, n)

-- 4.0.0
emb_rowid BIGINT IDENTITY PRIMARY KEY,
graph_id  VARCHAR(256) %EXACT NOT NULL DEFAULT '',
node_id   VARCHAR(256) %EXACT NOT NULL,
emb       VECTOR(DOUBLE, n),
metadata  %Library.DynamicObject,
CONSTRAINT uq_emb_graph_node UNIQUE (graph_id, node_id)
```

`emb_rowid` exists so the HNSW index is legal — IRIS refuses a vector index on a
table whose primary key is the vector's neighbour. `kg_NodeEmbeddings_optimized`
is identical with `uq_emb_opt_graph_node`.

**Anything reading or writing `id` on these tables must change to `node_id`.**
The failure modes are inconsistent, so test rather than reason:

| Statement                                 | 4.0.0 behaviour                |
| ----------------------------------------- | ------------------------------ |
| `SELECT id FROM kg_NodeEmbeddings`        | returns the **RowID**          |
| `... WHERE id = 'some:node'`              | `0` rows, **no error**         |
| `INSERT INTO ... (id, emb) VALUES (?, ?)` | `SQLCODE -108`, required field |

The middle row is the dangerous one: a filter on `id` is silently unsatisfiable.

### `nodes`, `rdf_labels`, `rdf_props`

`CONSTRAINT uq_nodes_nodeid UNIQUE (node_id)` becomes `UNIQUE (graph_id,
node_id)`. `rdf_labels` and `rdf_props` gain a `graph_id` and include it in
theirs, so a node ID present in two graphs holds a separate label set and a
separate property set per graph (FR-034). A label that exists only in another
graph no longer matches a label-filtered search (FR-035).

Consequence for writers: **an edge requires both endpoints in its own graph.**
`node_id` alone no longer identifies a node, so an endpoint is resolved as
`(graph_id, node_id)` and an edge cannot straddle two graphs.

### `rdf_edges` is no longer class-declared

`Graph.KG.Edge` is deleted. A class-declared `rdf_edges` has no `edge_id`, so
`rdf_edges` is DDL-declared in every namespace now, and `Graph.KG.Eraser` is the
marker class to probe for:

```sql
SELECT COUNT(*) FROM %Dictionary.ClassDefinition WHERE Name = 'Graph.KG.Eraser'
```

Zero means a DDL-only namespace: deploy `iris_src/src` into it before writing
data. `Graph.KG.Ledger.RebuildEdgeIndices` now rebuilds `rdf_edges` as well as
`^KG`.

**Your 3.2.0 edges are inside that class.** `Graph.KG.Edge` is declared
`[ Final, DdlAllowed, SqlTableName = rdf_edges ]`, which means the class owns the
extent: deleting it deletes every edge in the namespace. So the deploy stages the
rows first, rebuilds the table from DDL, and puts them back:

| Table                       | Holds                                              |
| --------------------------- | -------------------------------------------------- |
| `rdf_edges__ivg400rescue`   | every row staged before `Graph.KG.Edge` is deleted |
| `rdf_edges__ivg400unplaced` | rows the rebuilt table's foreign keys rejected     |

3.2.0's edge foreign key named `nodes (node_id)`; 4.0.0's is composite
(`graph_id, node_id`), so an edge whose endpoints do not both live in its own
graph fails `fk_edges_dest` with SQLCODE -121 on the way back in. Those rows are
quarantined, not deleted and not moved to a graph that would accept them:

```sql
SELECT graph_id, s, p, o_id FROM Graph_KG.rdf_edges__ivg400unplaced
```

Place one by creating the missing endpoint in that graph and re-inserting, or
correct its `graph_id` and re-insert. Once every staged row is accounted for as
placed or quarantined, the staging table is dropped; if the counts do not agree it
is left behind, because it is then the only surviving copy.

The rebuilt table also needs a key that does not exist yet on a 3.2.0 install. Its
two foreign keys reference `nodes (graph_id, node_id)`, and IRIS refuses a foreign
key whose referenced columns carry no unique key:

```text
SQLCODE -314: Foreign Key 'FK_EDGES_SOURCE' references non-unique column(s) in
table 'GRAPH_KG.NODES', column(s) 'GRAPH_ID,NODE_ID'
```

v3.2.0 declares `uq_nodes_nodeid UNIQUE (node_id)` and nothing composite, and the
composite key is otherwise added later — by the embeddings migration, which runs
after `initialize_schema` has already deleted the class. So the restore adds
`uq_nodes_graph_node` itself first. It is additive: 3.2.0's `node_id` was globally
unique, so `(graph_id, node_id)` cannot collide, `uq_nodes_nodeid` stays until the
embeddings migration drops it, and on a namespace that already has the composite
key the statement is a no-op.

A restore that fails **raises**, and every failure inside it raises as the same
`RdfEdgesRescueError` — not only a short row count. Both halves matter: the call
site logs an ordinary exception at DEBUG as "expected in Docker", so before this
the -314 above produced `initialize_schema` reporting `tables_created: True` and
`objectscript_deployed: True` over a namespace with no `Graph_KG.rdf_edges` at
all, its edges sitting in a staging table nothing had mentioned. If you are
looking at such a namespace from an earlier attempt, the rows are still there:

```sql
SELECT COUNT(*) FROM Graph_KG.rdf_edges__ivg400rescue
```

Drop the empty or missing `rdf_edges`, re-run `initialize_schema()`, and the
restore picks the staged rows back up.

Because the restore adds that key, `upgrade_to_4_0_0` then meets it again: the
embeddings migration re-keys `nodes` and issues the same `ADD CONSTRAINT`. IRIS
refuses the second one by the index name it derives from the constraint, and says
nothing about the constraint already existing:

```text
SQLCODE -400: ERROR #5067: Index name conflict: uqnodesgraphnode
```

That is now tolerated, so the upgrade runs to the end in one call. It matters
because the step that aborted on it was the one that gives `rdf_labels` and
`rdf_props` their `graph_id` — an upgrade stopping there leaves the child tables
unscoped and never reaches the `^KG` rebuild, which then refuses for a reason
(FR-028 below) that reads like a different problem entirely.

## Routed tables

A graph's vectors live in a table named for the pair `(graph_id, model_key)`:

```text
kg_emb_<first 16 hex of sha256(graph_id + "\0" + (model_key or ""))>
```

- **Opaque on purpose.** A readable `kg_emb_<graph>_<model>` breaks on two IRIS
  rules at once: DDL strips underscores when deriving a class name and
  de-duplicates collisions with a numeric suffix, and the derived class name has
  a 220-character ceiling. A hash sidesteps both and keeps a caller-supplied
  graph ID out of an identifier entirely.
- **One graph per table** (FR-037). A scoped read over a routed table does not
  need a graph predicate to be correct; it carries one anyway, so a table read
  through the wrong route still answers about the right graph.
- **Created by the first write** that names the pair, with its width taken from
  the vector being stored, and registered in `Graph_KG.embedding_registry`
  (keyed `(table_name, graph_id)`, indexed `(graph_id, model_key)`).
- **One HNSW index per routed table**, reported from
  `%Dictionary.CompiledIndex` rather than synthesized. `SHOW INDEXES` reports
  what exists.
- **Never derive a name to find a route.** `route_table_name()` says what a
  route *would* be called; the registry row is the only authority on what it *is*
  called, because IRIS may have derived a class name the table name does not
  predict.

A `(graph, model_key)` pair with no routed table yet **does not fall back to a
namespace-wide scan**. A read returns `None`/`[]`/`0`; a write creates the route.

Tested ceiling: **50 graphs × 2 models = 100 routed tables**. That is a measured
figure, not an architectural limit — see `docs/OPERATIONS.md` for the create and
drop cost per route.

## The quarantine

The migration places every pre-upgrade vector in a graph **or** quarantines it.
It never assigns an ambiguous row to the default graph (FR-028).

`Graph_KG.embedding_quarantine` holds those rows with their node ID, source
table, vector, width, dtype, and a reason:

| Reason              | Meaning                                            |
| ------------------- | -------------------------------------------------- |
| `ambiguous_graph`   | more than one graph holds a node with that ID      |
| `no_node`           | no node holds that ID at all                       |
| `resolver_declined` | a resolver was offered the row and returned `None` |

No search path reaches the quarantine. A quarantined vector does not become
searchable by sitting still — an operator moves it, one row at a time:

```python
for row in engine.list_quarantine(reason="ambiguous_graph"):
    print(row.q_rowid, row.node_id, row.source_table, row.dimension, row.reason)

engine.place_quarantined(row.q_rowid, graph="graphA", model_key="bge-small")
```

A listing carries no vectors. A placement copies the vector inside IRIS with an
`INSERT ... SELECT`, so the floats never become text and back (ADR-0005), and a
listing that returned a few thousand 768-wide arrays would bury the reasons an
operator is reading it for. `dimension` is the width the row's vector actually
has: the quarantine's own `emb` declares a type and no length, precisely so rows
of different widths can sit next to each other.

`place_quarantined` refuses — raising, leaving the row where it is — when the
pair has no route, when the route's declared width or dtype disagrees with the
row's, or when the node does not exist *in that graph*. It never creates a
route: creating one would declare a width taken from a row whose provenance is
the thing in doubt.

To avoid the quarantine entirely, hand the migration a resolver:

```python
def resolve(v):  # v is an AmbiguousVector
    return v.candidate_graphs[0] if "tenant-a" in v.candidate_graphs else None

report = migrate_to_graph_scoped_embeddings(conn, resolver=resolve)
```

Returning `None` declines the row, which quarantines it. Declining and having no
resolver reach the same placement and differ only in the recorded reason.

## Reading the report

`upgrade_to_4_0_0` returns an `UpgradeReport`: one `StepResult` per step, in
execution order, each carrying that step's own report or the reason it was declined.

```python
report.names               # ('embeddings', 'docs', 'edge_vectors', 'kg_node_stores')
report.skipped             # the steps that found their work already done
report.rows_accounted      # placed + quarantined across the steps that count rows
report["docs"].report      # a PlacementReport, or None when skipped
report["docs"].skipped_because
```

A `PlacementReport` (the `docs` and `edge_vectors` steps) describes **this pass**:
`rows_placed` keyed by graph, `rows_quarantined` keyed by reason, `quarantined_keys`,
and `rows_accounted`, which must equal the rows that pass found. A second pass over a
finished migration legitimately reports `rows_accounted == 0` — or, more usually,
reports itself skipped. The embeddings report below describes the **install's state**
instead, so a resumed run reports the whole install rather than its own half.

```python
report.rows_placed          # {(table, graph): count}
report.rows_quarantined     # {reason: count}
report.quarantined_ids
report.tables_created
report.indexes_created
report.indexes_refused      # {table: reason}
report.widths_reconciled    # {table: (recorded, actual)}
report.structural_blockers  # {child_table: [node_id, ...]}
report.rows_accounted       # placed + quarantined
```

`rows_accounted` must equal the pre-upgrade row count, with zero deleted
(FR-026). The arithmetic is derived from the state the migration left, not from a
log of what this pass did, so a resumed run reports the whole install rather than
its own half.

A non-empty `structural_blockers` means the `rdf_labels`/`rdf_props` re-key was
**refused, not attempted**: a child row whose node is not in exactly one graph
has no recoverable graph, and `MIN(graph_id)` would be the silent version of
this migration. Resolve those nodes, then re-run.

A refused re-key stops the embedding reshape too, so a blocked run writes
nothing and reports what it *would* place, as a dry run does. The reason is
`nodes`: while it still keys `node_id` alone, the composite `fk_emb_node` the
rebuilt table declares has nothing to point at (`SQLCODE -121`), and reshaping
without it would leave the default route with no reference to `nodes` while
every generated route has one.

## Python API changes

New keyword-only `graph` (and `model_key` where a route is selected) on:

`store_embedding`, `store_embeddings`, `get_embedding`, `get_embeddings`,
`embed_nodes`, `embedding_count`, `attach_embeddings_to_table`, `vector_search`,
`kg_KNN_VEC`, `kg_RRF_FUSE`, `HybridSearchFusion.multi_modal_search`,
`node_exists`.

In every one, `graph=None` means **the default graph** (`''`), never every graph.
A scoped lookup never falls back to an unscoped scan.

One exception, and it raises rather than defaulting: `vector_search` aimed at a
routed table (`kg_emb_<hash>`) with no `graph` **refuses** (FR-041). That table
holds one graph's vectors for one model, so `''` would ask for the default
graph's rows from a table that does not hold them, and dropping the predicate
would scan the route. The test is the table *name*, not a registry lookup — the
refusal must not depend on a database read. Aimed at any other table,
`vector_search` behaves as it did in 3.2.0.

Removed:

- `GraphSchema.get_procedures_sql_list(embedding_dimension=...)` — inert since
  it was added; passing it is now a `TypeError`. The query vector is converted
  with an unlengthened `TO_VECTOR` on purpose (ADR-0005): a declared length makes
  IRIS reshape the query vector and score the reshaped value, returning a perfect
  `1.0` for a query that should have raised `SQLCODE -257`.
- `kg_KNN_VEC`'s `embeddingConfig` — the slot is the graph now.

## Snapshot format

Node records changed from `{"id": ...}` to `{"graph_id": ..., "node_id": ...}`.
Reads accept **both**, so a 3.2.0 snapshot restores into 4.0.0; a 4.0.0 snapshot
does not restore into 3.2.0.

## Cypher

`n.id` is `n.node_id`. A property named `id` on a node is now just a property.

## Ordering trap: `initialize_schema` before the migration

An upgraded package meeting a 3.2.0 table cannot compile `kg_KNN_VEC` — the
4.0.0 body reads `n.node_id` and `n.graph_id`, and a table still keyed `id` has
neither. The migration that fixes the table needs `embedding_quarantine`, which
only `initialize_schema` creates, so each would be a prerequisite of the other.

Instead: `initialize_schema()` **defers** `kg_KNN_VEC` on a pre-migration
install, logs a warning naming the migration call, and installs every other
procedure. The migration installs `kg_KNN_VEC` when it is done. Server-side
vector search is unavailable in between; nothing else is.

So the order is:

```python
engine.initialize_schema()          # warns, defers kg_KNN_VEC
upgrade_to_4_0_0(engine.conn)       # moves rows, installs it, re-keys the rest
```

`initialize_schema()` is also the prerequisite of the `^KG` step for a different
reason: that step reads each entry's graph off an `rdf_*` row, and refuses to kill
anything while those rows are still on the pre-214 shape.

`idx_docs_graph` is deferred the same way, and for the same reason: `Graph_KG.docs`
gains `graph_id` in the migration's `docs` step, so on a 3.2.0 install there is no
column to index yet. `initialize_schema()` skips the statement and logs

```text
idx_docs_graph deferred: Graph_KG.docs has no graph_id column on this install...
```

The `docs` step creates the index when it has placed the rows. Nothing else in the
schema is affected, and this is a deferral, not the `SQLCODE -31` a 3.2.0 install
used to report here.

## `docs` is keyed by graph, and `id` is a node ID

```sql
-- 3.2.0
id VARCHAR(256) %EXACT PRIMARY KEY, text VARCHAR(4000) %EXACT

-- 4.0.0
graph_id VARCHAR(256) %EXACT NOT NULL DEFAULT '',
id       VARCHAR(256) %EXACT NOT NULL,
text     VARCHAR(4000) %EXACT,
CONSTRAINT pk_docs PRIMARY KEY (graph_id, id)
```

**What breaks.** Two things, and the second is the reason for the first:

- A `docs` row was reachable by `id` alone. It now needs its graph too, and the
  BM25 leg of a scoped hybrid search sees only its own graph's documents.
- `id` is a **node ID**. In 3.2.0 it meant whatever the writer chose, which is why
  `kg_RRF_FUSE` fused nothing: the vector leg answers node IDs, so a
  `FULL OUTER JOIN` against free-form document IDs matched no pair and every
  "fused" row carried one leg and NULLs for the other. Fusion working at all
  depends on the two legs agreeing about what a row is called.

**What to run.** The `docs` step of `upgrade_to_4_0_0`, which places each row in
the graph holding the node its ID names:

```python
report = upgrade_to_4_0_0(conn, steps=("docs",))
print(report["docs"].report.rows_placed)       # {graph_id: rows}
print(report["docs"].report.rows_quarantined)  # {reason: rows}
```

A row whose ID names no node is quarantined `no_node`; an ID two graphs hold a node
for is `ambiguous_graph` unless a `document_resolver` picks one. Nothing is placed
in the default graph to make it fit: a document about graph B's node, sitting in the
default graph, reads and ranks exactly like an answer.

**Resolving a quarantined row.** `Graph_KG.docs_quarantine` holds the ID, the text
and the reason — everything needed to re-insert it. There is no `place_quarantined`
for a document, because placing one is an ordinary insert once its node exists:

```sql
SELECT doc_id, reason, text FROM Graph_KG.docs_quarantine ORDER BY reason, doc_id;

-- Once you know the graph, and the node exists in it:
INSERT INTO Graph_KG.docs (graph_id, id, text)
  SELECT 'tenant-a', doc_id, text FROM Graph_KG.docs_quarantine WHERE doc_id = ?;
DELETE FROM Graph_KG.docs_quarantine WHERE doc_id = ?;
```

If your corpus was keyed by document rather than by node — the common 3.2.0 case —
every row lands in `no_node` and the fix is to re-ingest with node IDs, not to pick
graphs one row at a time.

## Edge vectors are keyed by graph, and routed

```sql
-- 3.2.0
s, p, o_id  (composite primary key), emb VECTOR(DOUBLE, n)

-- 4.0.0
emb_rowid BIGINT IDENTITY PRIMARY KEY,
graph_id  VARCHAR(256) %EXACT NOT NULL DEFAULT '',
s, p, o_id,
emb       VECTOR(DOUBLE, n),
metadata  VARCHAR(4000),
CONSTRAINT uq_edge_emb_graph_spo UNIQUE (graph_id, s, p, o_id)
```

**What breaks.** In 3.2.0 two graphs asserting the same triple shared one row, so
the second write replaced the first silently. Now they are two rows, and an edge
vector reached by triple alone is ambiguous. Edge vectors also route per
`(graph_id, model_key)` exactly as node vectors do — same `kg_eemb_<hash>` naming,
same registry, same refusal to fall back to an unscoped scan — so a caller that
names a model reaches the route rather than the default table.

**What to run.** The `edge_vectors` step, whose placement reads each vector's graph
from `rdf_edges` — from the graph *asserting the edge*, never from endpoint
membership. A node can sit in a graph that never asserted this triple, and a vector
placed there would answer searches in a graph that has no such edge.

```python
report = upgrade_to_4_0_0(conn, steps=("edge_vectors",), edge_dimension=768)
```

`edge_dimension` is read off the source column when omitted; pass it when the
source declares no width. It must match the source, because IRIS checks a declared
VECTOR width at INSERT (`SQLCODE -104`).

**Resolving a quarantined row.** `Graph_KG.edge_vector_quarantine` holds the triple,
the reason and the vector. `no_edge` means no graph asserts the triple;
`ambiguous_graph` means more than one does and no `edge_resolver` chose. Move a row
with an `INSERT ... SELECT` so the vector stays inside IRIS (ADR-0005):

```sql
INSERT INTO Graph_KG.kg_EdgeEmbeddings (graph_id, s, p, o_id, emb, metadata)
  SELECT 'tenant-a', s, p, o_id, emb, NULL
  FROM Graph_KG.edge_vector_quarantine WHERE q_rowid = ?;
DELETE FROM Graph_KG.edge_vector_quarantine WHERE q_rowid = ?;
```

Assert the edge in that graph first. A vector for a triple the graph does not
assert is a search answer about an edge that is not there.

## The `^KG` node stores gain a graph subscript

| 3.2.0                      | 4.0.0                             |
| -------------------------- | --------------------------------- |
| `^KG("prop", s, key)`      | `^KG("prop", graph, s, key)`      |
| `^KG("label", label, s)`   | `^KG("label", graph, label, s)`   |
| `^KG("deg2p", s, p)`       | `^KG("deg2p", graph, s, p)`       |
| `^KG("deg2p_exact", s, p)` | `^KG("deg2p_exact", graph, s, p)` |

Spec 214 did this for `out`, `in`, `deg` and `degp` and left these four flat.

**What breaks, and how quietly.** A 4.0.0 reader on the 3.2.0 layout does not
fail — `$Data` and `$Order` on an absent subscript mean "nothing here". A
label-filtered traversal stops matching, a property map comes back empty, and a
two-hop count comes back `0`. Upgrading the package without this step is the
scenario where every one of those reads succeeds and answers nothing.

**What to run.** The `kg_node_stores` step. The entries are **dropped, not moved**:
nothing in a flat entry says which graph it belongs to, and `^KG("deg2p")` is worse
than ambiguous — the count was summed across every graph, so the number belongs to
no graph and no placement could make it true. The subtrees are killed and
`Graph.KG.TraversalBuild` rebuilds them from the SQL rows, each of which carries its
own `graph_id`:

```python
report = upgrade_to_4_0_0(conn, steps=("kg_node_stores",))
print(report["kg_node_stores"].report.entries_rebuilt)  # {store: {graph: entries}}
print(report["kg_node_stores"].report.entries_dropped)
```

There is no quarantine here, because there is nothing to hold: every statistic comes
back from the rows. The step raises **before killing anything** if `rdf_props`,
`rdf_labels` or `rdf_edges` has no `graph_id` — a rebuild from pre-214 rows would
send every entry to the default graph with nothing left to recover from. Run
`initialize_schema()` first in that case.

A source table that does not exist at all is reported as absent, not as a table
missing a column. The two are indistinguishable through
`INFORMATION_SCHEMA.COLUMNS` — both answer nothing — and the distinction is the
whole difference between the two fixes: the second message tells you to run
`initialize_schema()`, which is the step that had destroyed a class-owned
`rdf_edges` in the first place. So an absent source points at the staged rows
instead:

```text
... Graph_KG.rdf_edges does not exist. An upgrade from v3.2.0 reaches this when
the class-owned table was deleted without being rebuilt: look for the staged rows
in Graph_KG.rdf_edges__ivg400rescue...
```

It needs the ObjectScript classes deployed: a DDL-only namespace has no
`Graph.KG.TraversalBuild` to rebuild with. Probe for `Graph.KG.Eraser` as above.

**Deployed is not the same as compiled.** `initialize_schema()` deploys the
ObjectScript layer before anything gives `rdf_labels` and `rdf_props` their
`graph_id`, so on a 3.2.0 install `Graph.KG.TraversalBuild`'s embedded SQL compiles
against a column that is not there yet:

```text
ERROR: Graph.KG.TraversalBuild.cls — Field 'GRAPH_ID' not found in the applicable
tables^ DECLARE c1 CURSOR FOR SELECT s , label , graph_id FROM
```

The class is left with no compiled methods, and ordering `BuildKG` out of it fails
`ERROR #5123: Unable to find entry point`. So the step recompiles `Graph.KG` once the
columns exist, then checks `%Dictionary.CompiledMethod` for every rebuild entry point
**before the first `Kill`** — in a dry run too. If one is still missing it refuses by
name:

```text
the ^KG rebuild is ordered out of Graph.KG.TraversalBuild::BuildKG, and IRIS has no
compiled entry point for it... Nothing has been dropped.
```

Check the compiler output for that class — usually a source tree that was never
loaded into this namespace — then re-run. The `^KG` tree is untouched until the check
passes.

## The compile that switched text search off

An upgraded — or merely re-deployed — install could answer every text query with the
wrong engine and report nothing. The trigger is a second compile of the `Graph.KG`
package:

```text
[SQLCODE: <-149>] Index method Graph.KG.docsivg400.idxdocstextifindFind(...) failed
... <CLASS DOES NOT EXIST> idxdocstextifindEmbedded+2^Graph.KG.docsivg400.1
```

`%FIND search_index(idx, term)` does not reach the index directly. It calls a class the
compiler **generates** while compiling the index's owner: `<owner>.<hash>`, with
`GeneratedBy = '<owner>.CLS'`, extending `%iFind.Find.Basic`. Compile the package a
second time and that compiled helper is deleted and not rewritten, because the owner it
would be regenerated from is already up to date. Measured pass by pass on
`irishealth:2026.3.0AI.113.0`: pass 1 generates the helper, pass 2 removes it, pass 3
leaves it missing.

Two compiles is the ordinary case, not a contrived one. `initialize_schema()` deploys
the ObjectScript layer, and the `^KG` re-key recompiles the package so its embedded SQL
binds to the re-keyed rows — and a `LoadDir` deploy over an already up-to-date tree does
it on its own. Both of the schema's iFind indexes are affected: `idx_docs_text_ifind`
(the `kg_TXT` leg, and through it fused search) and `idx_props_val_ifind` (property text
search).

Nothing reported it because nothing was wrong anywhere it looks. The index is still in
`%Dictionary.CompiledIndex`, the class definition is intact, `SHOW INDEXES` lists the
row. Only a query notices, and `kg_TXT` caught the error and fell back to `LIKE` — which
matches substrings and scores every hit 1.0 — so the leg kept answering, differently.

4.0.0 repairs it where the damage is done. Both `initialize_schema()` and the `^KG`
re-key compile each affected owner class on its own, which always regenerates the helper,
then **re-read** to decide — the compiler's status is not the verdict.
`initialize_schema()` reports what it found:

```python
status = engine.initialize_schema()
status["ifind_indexes"]
# {'idx_docs_text_ifind': True, 'idx_props_val_ifind': True}
```

An index still unsearchable appears in `status["warnings"]` by name. If you hit the
`-149` from some other compile, the fix is one call per owning class:

```objectscript
Do $SYSTEM.OBJ.Compile("Graph.KG.docsivg400","ck")
```

or simply re-run `initialize_schema()`. `kg_TXT`'s warning now distinguishes this
failure — a defined index whose generated class is missing, repairable — from an index
that was never created, where the `LIKE` fallback is the answer.

## Remaining gap: the IVF and BM25 index structures

`Graph.KG.IVFIndex` is keyed by index name only and holds no graph, so an IVF answer
spans every graph in the namespace. 4.0.0 does not scope it — it **refuses** it:
`search_nodes_by_vector(..., graph=...)` or `model_key=...` raises rather than
falling back to the index (FR-013). An explicit default graph (`graph=""`) still
reaches IVF, because that is the same question the unscoped call asks.

A BM25 index is per index name too, but its corpus is `Graph_KG.docs`, which is now
graph-scoped, so the text leg of a scoped hybrid search is scoped by its rows.

## A graph ID is not an authorisation boundary

Client-supplied graph IDs are **collision avoidance**. Nothing in 4.0.0 stops a
caller who can reach the engine from naming another caller's graph. For tenant
isolation, use a separate IRIS namespace per tenant.
