# Migrating to 4.6.0: one IVG Schema per namespace

4.6.0 moves everything IVG creates in SQL into one schema per namespace, the **IVG Schema** (default `Graph_KG`), and
keeps IVG's ObjectScript classes in IVG's own packages (spec 262, ADR-0016). This page covers what changes for an
existing namespace, what to run, and what moved.

## In short

- A namespace that stays on `Graph_KG` needs no SQL changes. Run `initialize_schema()` once under 4.6.0 (look first
  with `initialize_schema(dry_run=True)`).
- IVG no longer uses the objects 4.5.x created in `SQLUser` and the `User` package, but it leaves them there and
  working, so SQL that calls them keeps answering. `engine.remove_legacy_objects()` lists them, and
  `remove_legacy_objects(dry_run=False)` removes them when you are ready.
- Other changes a caller must act on are listed under [Breaking changes](#breaking-changes), each with its one-line
  migration.
- The namespace, not the schema, is IVG's isolation unit: `^KG`, `^NKG` and `^IVG.*` belong to the namespace. One
  namespace holds one IVG Schema. To run two IVG graphs side by side, use two namespaces.

## Breaking changes

What a 4.5.x caller must change for 4.6.0, one line each, with what to do. The CHANGELOG has the full entry
for each, under Changed, Fixed and Removed.

- A Cypher read that fails comes back in `result.error`; it raised for weighted paths, variable-length patterns and
  `shortestPath`. If you caught the exception, pass `raise_on_error=True`.
- `count_nodes`, `get_nodes` and the property readers (`get_node_ids_by_property`, `get_property_pairs` and the
  rest) raise when their query fails; they answered `0` or `[]`. Catch the error where a failure is expected.
- Result lists, maps and paths are Python values: `execute_cypher`, Bolt and REST answer lists and dicts, nested ones
  too, instead of JSON text; a path is `{'nodes': [...], 'rels': [...]}`, a map projection a dict whose values keep
  their stored types, and a node inside a list or map (`collect(n)`, `[n]`, `{k: n}`, and one taken from such a list by `head()`, a
  subscript or `UNWIND`) a dict `{"_id", "_labels", "_props"}` whose `_props` entries are JSON text (`RETURN n` is still
  three JSON-text columns), and a relationship, returned by itself or inside a list or map (`collect(r)`), a dict
  `{"type", "props"}` (over Bolt, `RETURN r` is a Relationship). A string the query builds stays a string; a
  stored property string that spells a list, a map or a boolean still reads as one
  ([Known issues](../KNOWN_ISSUES.md#a-stored-string-that-spells-a-boolean-a-list-or-a-map-reads-as-one-and-u0000-as-the-empty-string)). Drop `json.loads` on result values.
- A list or map property reads as the list or map (Fixed: values): drop `json.loads` on `x.p` and `properties(n)`.
- With no `USE GRAPH`, `MATCH (a), (b)` pairs each graph's nodes only: for pairs across graphs, one `USE GRAPH` query
  per graph.
- `size()` of a number, a boolean or a map, and `abs`, `ceil`, `floor`, `round`, `sign`, `sqrt`, `exp`, `log`,
  `log10`, `sin`, `cos`, `tan`, `cot`, `asin`, `acos`, `atan`, `degrees`, `radians` and `haversin` of a string, a
  boolean, a list or a map, raise `TypeError` (they answered a number: `abs('a')` was 0, `sqrt(true)` 1): fix the
  query or catch the error. A null still answers null.
- IVG's SQL objects are in the IVG Schema (default `Graph_KG`), not `SQLUser`, and a namespace an earlier release set
  up is refused until `initialize_schema()` has run there: run it once per namespace (look first with
  `dry_run=True`), set `IVG_SCHEMA_PREFIX` only if your schema is not `Graph_KG`, and qualify your own SQL with the
  schema. The four `SQLUser` views are gone: read the tables.
- With `IVG_API_KEY` set, every route on every app needs the key, Bolt included: send `X-Api-Key` (or Bearer), and
  the key in Bolt's HELLO/LOGON.
- `cypher_api`'s `/health` answers only `{"status": ...}` with 200 or 503: read the status code.
- `sync()`, the algorithm methods and a refused write raise where they answered `False`, `[]`, `{}`, `None` or 0:
  `sync()` and a failed algorithm method raise `RuntimeError` naming the method, `bfs_vector_rerank` raises
  `NotImplementedError`, and a write IRIS or IVG refuses raises `GraphWriteError` (a `RuntimeError`). Catch the
  exception.
- `save_snapshot`, `restore_snapshot` and `bulk_ingest_edges` raise on a table or global they cannot read or write:
  handle `SnapshotReadError` / `RuntimeError`.
- `node_count()`, `edge_count()`, `count_nodes()`, `get_node_count()`, `get_edge_count()`,
  `get_label_distribution()` and the HTTP `/schema` and `/stats` counts count the default graph when no graph is
  given (`status()` still counts every graph): pass `graph=`, or add up the graphs.
- `delete_node(id)` and `bulk_delete_nodes(ids)` without `graph=` refuse an id two graphs hold: pass `graph=`.
- Without `USE GRAPH`, a `CALL` and a `WITH` stage answer each graph's own rows: add `USE GRAPH ''` for the default
  graph's.
- Seven `^NKG` procedures (`ivg.betweenness`, `ivg.closeness`, `ivg.eigenvector`, `ivg.leiden`, `ivg.triangleCount`,
  `ivg.scc`, `ivg.kcore`) refuse under `USE GRAPH` or once a named graph has edges, and the GDS shims refuse what they
  cannot honour: call the engine method, or keep a graph in a namespace of its own; drop unknown config keys.
- `ivg.shortestPath.weighted` honours `maxHops` (default 10): pass `maxHops` for longer paths.
- `shortestPath` and variable-length path functions name their columns as the RETURN writes them, and `khop` answers
  `{"nodes": [...], "edges": [...]}`: read columns by alias or item text.
- `YIELD <column> AS <name>` binds the name on every `ivg.*` procedure: rename an alias that clashed.
- Integer division truncates toward zero, and arithmetic on a zero divisor or a value of the wrong type fails with
  openCypher's `ArithmeticError` / `TypeError`: `toFloat(x) / 2` for a fraction; guard the operands. Where the
  query's text shows the error (`'a' - 1`) `execute_cypher` raises Python's `TypeError`; where IRIS meets it on a row
  (`1 / 0`, `n.name - 1`) the read fails as any read does ([User guide](../USER_GUIDE.md#errors)): `result.error`
  holds the openCypher name (`ArithmeticError: integer division by zero`), or `raise_on_error=True` raises
  `RuntimeError`.
- `<`, `<=`, `>`, `>=` between two durations answer null: compare their components.
- A CREATE or MERGE between matched nodes refuses a relationship property computed from the row: compute it in a
  `WITH`.
- `MERGE` with no `USE GRAPH` matches and creates in the default graph only, and `MERGE ... ON CREATE SET n = {...}`
  or `ON MATCH SET n = {...}` on a node is refused: add `USE GRAPH '<g>'`; use `SET n += {...}`, or a `SET` after the `MERGE`.
- A `SET`, `REMOVE`, `DELETE`, `MERGE` or `CREATE` after a `WITH` whose shape cannot be answered raises `SyntaxError`
  ("split the query"): split it into a read and a write.
- `create_edge` and `store_edge` refuse a NaN or infinite qualifier with `ValueError`: drop or encode such values.
- `ppr()` takes one seed or a list of node IDs and raises `TypeError` otherwise.
- The bulk loaders refuse rows that are not the documented shapes with `ValueError`: `bulk_create_nodes` and
  `bulk_create_edges` skipped a row missing a key and dropped unknown keys (`weight`, `qualifiers`, `label`),
  `bulk_create_edges_temporal` took a missing endpoint or timestamp, and `BulkLoader.load_nodes` / `load_edges` took a
  dict. Send the shape each method's docstring (API_REFERENCE) states.
- `kg_WCC` takes no `max_iterations` limit by default (it was 100) and raises "WCC did not converge" at one that is hit:
  drop `max_iterations=`, or raise it above the graph's diameter.
- An engine no longer sets the module-wide `set_schema_prefix`: call it yourself for an engine-less translation.
- `initialize_schema()`'s status keys say what the run did (`tables_created` is a list) and `routines` is spelled as
  the catalog does (`kg_PPR`): update scripts that read them.
- `IRISGraphEngine(EmbeddedConnection())` outside IRIS raises `EmbeddedUnavailableError`: run under `irispython` or
  connect over TCP.
- The `ai` extra, the benchmark and test-only classes, `User.Exec`, `GraphOperators`, `LIST_HEAD`, `LIST_LAST`,
  `User.funcSTRSPLIT`, `execute_weighted_shortest_path`, `NKGAccel.PPRNative` / `PPRJson` and the IPM module manifests are gone
  (Removed): drop them from install specs and vendored trees.
- `docker-compose.yml` names no container and takes its ports from `IVG_IRIS_PORT` / `IVG_WEB_PORT`: find the
  container with `docker compose ps`.
- The Arno loaders resolve one library path (`IVG_ARNO_LIB`, else a recorded path in the manager or binary directory,
  else `/usr/irissys/mgr/libarno_callout.so`): install the library there, or set `IVG_ARNO_LIB`.
- `eigenvector_centrality` and `CALL ivg.eigenvector` raise `PowerIterationFailedConvergence` when `max_iter` rounds do
  not converge (they answered the last round): catch it, or raise `max_iter` (at most 1000) or `tol`.
- `eigenvector_centrality`'s default `max_iter` is 100, not 30 (and `ivg.eigenvector`'s `maxIter`): pass
  `max_iter=30` to keep the old bound, which now raises where it does not converge.
- A direction outside `"out"`, `"in"` and `"both"` (`"out"` and `"in"` for the temporal reads) raises `ValueError`,
  in every method and procedure that takes one: pass one of those.

## Upgrading a namespace

1. `pip install -U iris-vector-graph`.
2. Look before you change anything:

   ```python
   engine = IRISGraphEngine(conn, embedding_dimension=768)  # schema_prefix= if yours is not Graph_KG
   print(engine.initialize_schema(dry_run=True))
   ```

   The dry run writes nothing. It returns the schema it would record (`schema`), how it chose it
   (`schema_recorded`: `new`, `existing`, `inferred` or `explicit`), how many 4.5.x objects are still in `SQLUser`
   and `User` (`legacy_objects`), the grants it would copy (`grants_copied`), the 4.5.x Arno functions it would
   replace or revoke grants on (`arno_wrappers_replaced`, `legacy_arno_revoked`; see
   [The 4.5.x Arno functions](#the-45x-arno-functions)), and any other schema holding IVG tables (`other_schemas`).

3. Run `engine.initialize_schema()`. It creates IVG's functions and procedures in the IVG Schema and copies every
   privilege granted directly on a 4.5.x `SQLUser` function or procedure to its replacement. It also drops compiled
   native plans built against the 4.5.x names, and records the schema in `^IVG.Deploy("schema")`. A role that could
   run Cypher before the upgrade still can afterwards.

### Until you upgrade

The 4.6.0 package refuses a namespace that no 4.6.0 `initialize_schema()` has recorded. The first database call raises
`IVGSchemaError` ("set up by an earlier IVG release ... Run initialize_schema()") before it sends any SQL, instead of
failing later with a missing-function error. `engine.status()` does not raise; it reports `schema: None` and gives the
reason. The 4.5.x `SQLUser` objects keep answering SQL that calls them directly.

### Choosing another schema name

`IRISGraphEngine(conn, schema_prefix="RAG")` or `IVG_SCHEMA_PREFIX=RAG` (the argument wins; `IRIS_SCHEMA_PREFIX`,
which iris-vector-rag reads, is never read by IVG). The name must match `[A-Za-z][A-Za-z0-9_]*`, must not be `SQLUser`
or start with `%`, and its class package (the name with `_` turned into `.`) must not be IVG's own (`Graph.KG`, `IVG`,
`IVGC`) or already hold someone else's classes.

Once a namespace records its IVG Schema, an engine built for another schema is refused on its first database call
with `IVGSchemaError` naming both. Nothing is written. Renaming a recorded schema is not supported in 4.6.0.

### A namespace whose IVG tables are in another schema, or in two

With no record, `initialize_schema()` decides which schema to record from where IVG's tables are:

| IVG's tables are in                     | Engine's schema named explicitly? | Result                                         |
| --------------------------------------- | --------------------------------- | ---------------------------------------------- |
| no schema                               | either                            | the engine's schema is recorded (`new`)        |
| the engine's schema only                | either                            | it is recorded (`inferred`)                    |
| another schema, or several              | no (the `Graph_KG` default)       | `IVGSchemaError` listing each with row counts  |
| several, the engine's schema among them | yes                               | it is recorded (`explicit`), the others listed |

A 4.x engine built with `schema_prefix="RAG"` queried `RAG`'s tables, but its `initialize_schema()` created
`Graph_KG`'s, so a namespace like hipporag2-pipeline's can hold IVG tables in both. To end with one schema, drop or move
the other schema's tables, then record. (Naming the schema to keep, with `schema_prefix=`, also records it with the
other schema's tables still there, and leaves them untouched.)

1. Keep anything you need from the other schema (call it `OTHER`). Copy its rows into the schema you keep with your
   own `INSERT ... SELECT`, or export them first. The steps below delete them.
2. Drop the other schema's IVG tables. When `OTHER` is `Graph_KG` and the 4.5.x `SQLUser` views are still there, drop
   those views first, because IRIS refuses to drop a table a view reads (SQLCODE -321). Skip the four `DROP VIEW`
   lines when they are gone. The list drops child tables before their parents. Drop a per-graph embedding table
   (`kg_emb_*`, and `kg_eemb_*` for edges) in `OTHER` the same way. Leave `OTHER`'s ledger tables (`ledger_revisions`
   and `ledger_stats`) for step 4: 4.5.x made them in `Graph_KG` whatever the prefix, so when `OTHER` is `Graph_KG`
   they hold the revision history, which step 3 copies.

   <!-- consolidation-drop -->

   ```sql
   DROP VIEW SQLUser.rdf_edges;
   DROP VIEW SQLUser.rdf_labels;
   DROP VIEW SQLUser.rdf_props;
   DROP VIEW SQLUser.nodes;
   DROP TABLE IF EXISTS OTHER.rdf_reifications;
   DROP TABLE IF EXISTS OTHER.rdf_edges;
   DROP TABLE IF EXISTS OTHER.rdf_labels;
   DROP TABLE IF EXISTS OTHER.rdf_props;
   DROP TABLE IF EXISTS OTHER.kg_NodeEmbeddings_optimized;
   DROP TABLE IF EXISTS OTHER.kg_NodeEmbeddings;
   DROP TABLE IF EXISTS OTHER.kg_EdgeEmbeddings;
   DROP TABLE IF EXISTS OTHER.kg_NodeEmbeddings_optimized_ivg400;
   DROP TABLE IF EXISTS OTHER.kg_NodeEmbeddings_ivg400;
   DROP TABLE IF EXISTS OTHER.embedding_quarantine;
   DROP TABLE IF EXISTS OTHER.embedding_registry;
   DROP TABLE IF EXISTS OTHER.docs;
   DROP TABLE IF EXISTS OTHER.fhir_bridges;
   DROP TABLE IF EXISTS OTHER.fhir_canonical_refs;
   DROP TABLE IF EXISTS OTHER.fhir_unresolved;
   DROP TABLE IF EXISTS OTHER.fhir_definitions;
   DROP TABLE IF EXISTS OTHER.fhir_graphs;
   DROP TABLE IF EXISTS OTHER.code_crosswalk;
   DROP TABLE IF EXISTS OTHER.kg_BM25Meta;
   DROP TABLE IF EXISTS OTHER.kg_IVFMeta;
   DROP TABLE IF EXISTS OTHER.kg_PlaidMeta;
   DROP TABLE IF EXISTS OTHER.rdf_namespaces;
   DROP TABLE IF EXISTS OTHER.relationship_mappings;
   DROP TABLE IF EXISTS OTHER.table_mappings;
   DROP TABLE IF EXISTS OTHER.nodes;
   ```

3. Record the schema you keep. Its tables are now the only IVG tables, so it is `inferred` (the ledger tables left in
   `OTHER` do not count). When the schema you keep is not `Graph_KG` and its ledger tables are empty,
   `initialize_schema()` copies the rows of `Graph_KG.ledger_revisions` and `Graph_KG.ledger_stats` into them, so
   `history()` and `verify()` keep the revision history. The status reports the rows copied as `ledger_history_copied`
   (`{}` when there was nothing to copy), and a dry run reports what it would copy:

   <!-- consolidation-record -->

   ```python
   engine = IRISGraphEngine(conn, embedding_dimension=EMBEDDING_DIMENSION, schema_prefix="RAG")  # your width
   status = engine.initialize_schema()
   assert status["schema"] == "RAG"
   ```

4. Drop `OTHER`'s ledger tables, now that step 3 has copied what they held. The revision table refuses to delete a row
   (the ledger is append-only), so a plain `DROP TABLE` of one that holds rows fails with ERROR #5764 ("%DeleteExtent
   could not delete all instances"). `%NODELDATA` drops the tables and leaves their rows where they are, in
   `^Graph.KG.LedgerRevisionD` and `^Graph.KG.LedgerStatsD`, which nothing reads once step 3 has copied them. When
   `OTHER` is not `Graph_KG`, 4.5.x made no ledger tables in it, and these statements drop nothing:

   <!-- consolidation-ledger-drop -->

   ```sql
   DROP TABLE IF EXISTS OTHER.ledger_revisions %NODELDATA;
   DROP TABLE IF EXISTS OTHER.ledger_stats %NODELDATA;
   ```

5. Rebuild the adjacency index from the schema you kept. `^KG` belongs to the namespace, and the dropped schema's rows
   wrote to it too:

   <!-- consolidation-rebuild -->

   ```python
   engine.sync()
   ```

`tests/e2e/test_262_not_upgraded.py` runs these four blocks as written, on a namespace that 4.5.1 left with IVG tables
in `Graph_KG` and `RAG`, and again with 4.5.1's ledger enabled, where `history()` and `verify()` answer the three
revisions 4.5.1 committed.

## Your own SQL that calls IVG's functions

4.6.0 creates every IVG function in the IVG Schema, and IVG's own queries name it there (`Graph_KG.STR_SPLIT`,
`Graph_KG.CY_CMP`). Until you remove the 4.5.x objects, SQL you wrote against them (`SELECT SQLUser.STR_SPLIT(...)`,
or an unqualified `STR_SPLIT(...)`, which resolves in `SQLUser`) keeps answering from the 4.5.x copies. Before you run
`remove_legacy_objects(dry_run=False)`, change that SQL to name the IVG Schema. A grant you made on a 4.5.x function
was copied to the new one by `initialize_schema()`. A grant on one of the four 4.5.x `SQLUser` views has no
replacement, because 4.6.0 creates no views. Grant `SELECT` on the IVG Schema's table instead (`Graph_KG.nodes`
rather than `SQLUser.nodes`). The view read `nodes` without `graph_id`, so it also showed every graph's nodes mixed
together.

4.6.0's Cypher calls functions that 4.5.x did not have. Every `RETURN n.prop` reads through `CY_TYPED`, for example.
So neither a copied grant nor SELECT alone lets a user run the queries it ran before. Every `initialize_schema()`
therefore grants EXECUTE on the functions of the Cypher read path to each user or role that holds either of these:

- EXECUTE on one of those functions, which a role that ran Cypher on 4.5.x holds once its grants are copied;
- SELECT on `Graph_KG.rdf_props`, granted on the table or on the schema. A grant on some of its columns does not count.

The read path is every function setup creates, or `Graph.KG.SqlProcs` projects, that reads nothing outside the
caller's SQL privileges: the `CY_*`, `CypherFn_*`, `JSON_*`, `LIST_*`, `STR_SPLIT`, `REGEX_MATCH`, `RAND`, `NEWID` and
`Percentile_*` functions, including any a later release adds. These functions reshape the values they are given, or
read rows through SQL as the caller, so the grant shows a user nothing it could not already SELECT. The
variable-length path functions (`CY_VLP_*`) are on it too: `CY_VLP_ENDS` reads `^KG`, and checks first that the
caller holds SELECT on the edge table. The other functions that read `^KG`, `^NKG` or an index global are left out:
the `kg_*` algorithms and searches, `MatchEdges`, `DijkstraPath`. The status lists each grant made under
`read_path_grants`, with the privilege that qualified the grantee under `because`; a dry run lists the grants it would
make. Setup grants EXECUTE on functions only, never SELECT on a table. The way to grant Cypher access is still the one
in [ADMIN_GUIDE, Privileges](../ADMIN_GUIDE.md#3-privileges): `GRANT EXECUTE ON SCHEMA Graph_KG` (and `SELECT ON
SCHEMA`) to the role.

## The 4.5.x Arno functions

4.5.x created its `ivg_arno_*` SQL functions on the first Arno call, without naming a schema, so they went into the
instance's default SQL schema. That is `SQLUser` unless the instance is configured otherwise. Each one loads any
library on the server and calls any function in it, for a caller holding EXECUTE on it and the `%System_CallOut`
resource. 4.6.0's copies open only the library `Graph.KG.ArnoAccel.LibPath()` resolves, and call only the functions
IVG uses ([ADMIN_GUIDE, Privileges](../ADMIN_GUIDE.md#3-privileges)). Every `initialize_schema()` finds each function
of those 19 names in the namespace, in any schema:

- In the IVG Schema, a copy that does not check (a 4.5.x one, made there because it was the default schema) is
  replaced by 4.6.0's text. Its grants stay. So is the IVG Schema's copy of a `SQLUser` function whose grants setup
  copies: 4.5.x made them on first use, so it may not exist yet. The status lists each one under
  `arno_wrappers_replaced`.
- In any other schema, setup revokes EXECUTE from every user and role that was granted it on the function, except a
  holder of `%All`, which may call it anyway. The functions stay. The status lists each revoke under
  `legacy_arno_revoked`, with the function, its schema, the grantee and who granted it. A grant through
  `GRANT EXECUTE ON SCHEMA` cannot be revoked on one function, so setup leaves it and adds a warning naming the
  grantee. Revoke that schema grant yourself, or remove the function (`remove_legacy_objects(dry_run=False)` for the
  `SQLUser` ones).

The dry run lists both under the same keys and changes nothing. A second run finds nothing to revoke or replace. SQL
that calls a 4.5.x Arno function directly is refused after the upgrade (SQLCODE -99) unless the caller holds `%All`.
Call the IVG Schema's copy instead: a grant on the `SQLUser` copy was copied to it.

## For projects that vendor IVG's sources

If your repository carries a copy of IVG's `iris_src/src` (opsreview does, with local fixes) and loads it yourself,
these are the changes to carry over. A namespace that stays on `Graph_KG` needs no SQL changes. Load the 4.6.0 classes,
then run `initialize_schema()` once, because the functions are created by its DDL, not by the classes.

### Moved classes

| 4.5.x class                     | 4.6.0                            | SQL it projects                                       |
| ------------------------------- | -------------------------------- | ----------------------------------------------------- |
| `User.CypherFn`                 | `Graph.KG.CypherFn`              | `CypherFn_IVG*` in the IVG Schema (was `SQLUser`)     |
| `User.funcJSONKEYS`             | `Graph.KG.JsonKeys`              | `JSON_KEYS` in the IVG Schema (was `SQLUser`)         |
| `User.funcSTRSPLIT`             | removed; `STR_SPLIT` is DDL only | `STR_SPLIT` in the IVG Schema, created by setup's DDL |
| `User.SQL`                      | `Graph.KG.SQL`                   | none                                                  |
| `PageRankEmbedded` (no package) | `Graph.KG.PageRankEmbedded`      | none                                                  |

On an IVG Schema other than `Graph_KG`, the deploy rewrites the classes' SQL for that schema as it loads them. The SQL
functions IVG's classes project are all declared by `Graph.KG.SqlProcs`, and it, `Graph.KG.LedgerRevision` and
`Graph.KG.LedgerStats` are the only classes that compile into the schema's package (`IVGALT.SqlProcs` for `IVGALT`),
so the functions land in the IVG Schema; `Graph.KG.CypherFn`, `Graph.KG.JsonKeys` and the rest stay in `Graph.KG`. If you load the sources yourself on such a namespace, load them through
`initialize_schema()` (or `iris_vector_graph._engine.class_deploy.deploy_packaged_classes(conn, schema=...)`), not with
`$system.OBJ.LoadDir`, or they will name `Graph_KG`.

### Retired classes

These no longer ship, and 4.6.0 never deploys them: `Graph.KG.Benchmark` and `Graph.KG.BenchFormat` (benchmark
code), `User.Exec` (runs `Xecute` on any string), `iris.vector.graph.GraphOperators`, and `Graph.KG.Loader` (a file
loader 3.2.0-4.2.3 shipped). Nothing called
GraphOperators' SQL procedures (`iris_vector_graph.kg_TXT`, `kg_KNN_VEC`, `kg_RRF_FUSE`); IVG's own `kg_TXT`,
`kg_KNN_VEC` and `kg_RRF_FUSE` are procedures in the IVG Schema. IVG's tests deploy these classes themselves from `iris_src/dev`. Drop
them from your copy, or keep them out of production namespaces.

### Functions and views 4.5.x created in `SQLUser`

Every one of these now lives in the IVG Schema under the same name, except where noted. The 4.5.x copies stay in
`SQLUser` until `remove_legacy_objects(dry_run=False)`.

- Created by 4.5.x setup (46), most with DDL; the 17 `CypherFn_*` and `JSON_KEYS` were projected by its
  `User.CypherFn` and `User.funcJSONKEYS` classes, as 4.6.0's `Graph.KG.SqlProcs` projects them in the IVG Schema
  ([Admin guide](../ADMIN_GUIDE.md) §2): `CY_CMP`, `CY_DURATION_FIELD`, `CY_EXP_ORDKEY`, `CY_EXP_ORDVAL`, `CY_PROPS_MAP`,
  `CY_RETYPE_MAP`, `CY_REVERSE`, `CY_SORT_KEY`, `CY_TEMPORAL_ARITH`, `CY_TEMPORAL_FIELD`, `CY_VLP_CHAIN`,
  `CY_VLP_DISJOINT`, `CY_VLP_ENDS`, `CY_VLP_HAS`, `CY_VLP_OPT`, `CY_VLP_PATHS`, `CypherFn_IVGJSONARRAYLENGTH`,
  `CypherFn_IVGJSONKEYS`, `CypherFn_IVGJSONREMOVE`, `CypherFn_IVGJSONSET`, `CypherFn_IVGJSONVALUE`,
  `CypherFn_IVGLISTGET`, `CypherFn_IVGLISTHEAD`, `CypherFn_IVGLISTLAST`, `CypherFn_IVGLISTREVERSE`,
  `CypherFn_IVGLISTTAIL`, `CypherFn_IVGMAPGET`, `CypherFn_IVGNEWID`, `CypherFn_IVGRAND`, `CypherFn_IVGRANGE`,
  `CypherFn_IVGREGEXMATCH`, `CypherFn_IVGSTRSPLIT`, `CypherFn_IVGTYPEERROR`, `JSON_ARRAYGET`, `JSON_ARRAYLENGTH`,
  `JSON_KEYS`, `JSON_VALUE`, `LIST_CONCAT`, `LIST_REVERSE`, `LIST_TAIL`, `NEWID`, `RAND`, `REGEX_MATCH`,
  `STR_SPLIT`, and `LIST_HEAD` and `LIST_LAST`, which are retired: 4.6.0 creates neither, because nothing called them

### Your own `User.*` classes

IVG 4.6.0 creates nothing in `SQLUser` or the `User` package, and its setup leaves classes there alone, including
ones named like IVG's (a `User.funcSTRSPLIT` or `User.CypherFn` of your own; `tests/e2e/test_262_vendored.py` checks
that their definitions are unchanged). `remove_legacy_objects()` works by name from the 4.5.x manifest, though, so a
class of yours that has a 4.5.x name (`User.funcSTRSPLIT`, `User.CypherFn`, `User.SQL`, `User.Exec`) is on its list.
Read the dry run's list before you run `remove_legacy_objects(dry_run=False)`, and rename your class first if you want
to keep it.
