# The alternative implementation against the 4.2.3 baseline, Neo4j and others

Generated by `python -m scripts.bench.alt.build_report` from the result files in
[`alt-bench/results/`](alt-bench/results). Method: [alt-bench/PROTOCOL.md](alt-bench/PROTOCOL.md). Suites:
[alt-bench/CATALOG.md](alt-bench/CATALOG.md). Earlier micro-level numbers: [alt-impl/PERF.md](../research/alt-impl/PERF.md).
Nothing here is published or pushed.

## Verdict

- **Parity is reached, within the measurement noise of this machine, with named exceptions.** The last code change was
  followed by a full re-measurement on a freshly restarted container (`final-1`, `final-2`, `final-3`; 5 to 7 interleaved
  repetitions; side B's tree checked identical to the committed branch). That is 264 compared metrics (three suites were
  measured twice): 5 faster, 249 at parity, 10 slower. The ten slower rows are `S.Q5` twice (the baseline answers that query with a tautology that ignores both
  parameters; the alternative does the lookup), `cypher-parser-bench` q4 twice (a client-side control, 0.5 microsecond on
  the average of a cached parse: a garbage-collector pause that lands in that query in side B's process because the connection
  shim loads more objects there; with `gc.disable()` the two sides are equal, 1.0 against 0.9 to 1.0 microseconds), two betweenness rows (0.7 to 1.11
  across passes: noise), two bidirectional-PPR timing tests (below: the baseline's stored counters double across the test's two fixtures; not a cost), and `ic13` and
  `test_05_2hop_traversal` once each (neither recurred in the 7-rep re-run). The breadth runs (migration, FHIR, index
  maintenance, the 100,000-node graph, the full DRKG load) are counted separately below.
- **The slowdowns measured before the fixes were real.** The first benchmark pass had `KHopCount` 270x to 18,000x slower
  because every degree was recounted on every read; the generation-validated cache, the whole-graph warm stamp and the single
  writer module fixed that. Three further regressions found while benchmarking are listed in the next section with their fixes.
- **Against Neo4j and Memgraph the picture is mixed and depends on the query shape** (caveats below before comparing):
  - Neo4j is faster than IVG on the count-style variable-length queries over the RMAT graphs (Q2 to Q4, spec-193
    `[*1..N]`), because IVG's `BFSFastJson` entry points ship every edge. IVG is faster on weighted shortest path (Q6), on
    LDBC IC3 and IC13 (like-for-like 10,000-row graph), and on exact betweenness, degree and Leiden at 2,000 nodes; GDS is
    faster on closeness and on exact betweenness at 500 nodes.
  - Memgraph is fastest on shallow queries (1-hop, IC2, friend count) and on small graphs, and falls far behind IVG as depth
    and size grow (depth 4 on the 10,000-node graph: 5.2 s against 130 ms; depth 3 on the 100,000-node graph: 3.6 s against
    0.7 s).

## Machine, sides and method

- One macOS host; IRIS 2026.3.0AI.113 enterprise in `ivg-iris-enterprise` (one container, two namespaces, `IVGBENCHA` and
  `IVGBENCHB`); Neo4j 5.24.2 Community with GDS 2.12.0, Memgraph 3.9.0, networkx 3.7, python-igraph 1.0.0 in other containers
  or a venv on the same Docker VM (8 CPUs, 64 GB). Competitors ran one at a time, never alongside an IRIS run.
- **Side A** is the 4.2.3 release (`6f17be0f`) with its own Python tree; **side B** is branch `alt-parity` (the alternative:
  one writer module for the adjacency, a generation-validated degree cache, no stored `deg`/`degp`). A and B were run
  interleaved (A, B, A, B, ...) so drift hits both. Per-run commits and load averages are in each run's `manifest.json`.
- Background load on this host was a load average of 8 to 14 during the timed runs (security agents, the macOS window server, OrbStack);
  two unrelated debug processes that were using about 1.7 cores were stopped first. Drift between sessions, measured on side A
  itself: 0 % to 6 % on the Q1 to Q6 medians between the confirmation passes and the end-of-session pass (side B: -2 % to +9 %). Treat differences inside roughly
  10 % as not distinguishable from drift.
- Verdict rule (`PROTOCOL.md`): parity when B/A is at most 1.10 or B's median lies inside A's spread; faster below 0.90;
  otherwise slower. A sub-microsecond metric is judged by absolute difference (0.25 microseconds); that rule was added after
  seeing the first measurement and is disclosed there.

## What happened on the way (read this before trusting any number)

1. **Run `core-2` is not used.** Partway through it IRIS stopped responding: the Write Daemon stalled and IRIS paused all
   users, after hours of multi-gigabyte loads on a container that had been up for days. I restarted the container. After the
   restart the same suite ran in 33 s instead of about 220 s, so everything taken before the freeze in that run was degraded.
   Its five completed suites were re-run (`core-4`); `core-2` stays in the repository, labelled, and is excluded from every
   count below. `core-1` ran earlier and before the translator fix; it is kept as the "before" picture.
2. **Three regressions were found and fixed during the run**, none of them the cache design:
   - 4.2.4's parameter-isolation walk in the Cypher translator took 80 % of `translate_to_sql` (0.03 ms to 0.15 ms on a
     short query). It is now cached on the cached syntax tree (no clash: one attribute read) and copy-on-write when a name
     really clashes.
   - A bulk load left the degree cache empty, so the first read after a load paid a recount per node (`perf-head-to-head`:
     load 1.58x, degree 2.3x). The bulk-load session now warms the cache once before the two-hop statistics.
   - Bulk readers paid three global reads per node where the stored counter paid one; a whole-graph "warm" stamp (valid
     while no write has bumped `^KG("__version")` since the cache was filled) brought that to one.
3. **Baseline A accumulates drift that the benchmarks do not clean up.** The bidirectional-PPR performance tests deleted
   rows by SQL and left `^KG` behind, so on side A each repetition walked a different, smaller graph (the result size varied
   between runs: 995, 989, 909, 492 nodes) and looked faster; side B always returned the same answer. From a clean state both
   sides return identical results and first-call times within about 10 %.
4. **A claim in ADR-0004 does not hold in the engine.** The engine's Native API handle is a dedicated connection, so a SQL
   `rollback()` does not undo adjacency written through it. A caller who disables autocommit and rolls back by SQL leaves
   adjacency behind, on the baseline as well. The rollbacks the engine guarantees are the ones ObjectScript owns.

## Parity: IRIS, alternative against baseline

Counts of compared metrics per run (the rule above; `slower` rows are listed under each run).

{{PARITY_COUNTS}}

`core-1` is before all the fixes, `core-3` and `core-4` after the translator fix but before the bulk-load warm-up,
`confirm-1`, `confirm-2` and `drift-1` after all of them, and `final-1` to `final-3` after the last change. The `core-4` rows (a node-delete test, a concurrent-throughput test and
`q3.p95`) and the `core-3` head-to-head rows did not reproduce at 5 repetitions in `confirm-2`. The slower rows left in the
final passes are:

- `S.Q5` shortest path, +0.08 to +0.1 ms (0.27 to 0.37 ms). The query is `shortestPath((a {node_id: $a})-[*..8]-(b {node_id:
  $b}))`: it names a pattern variable and a parameter alike. The baseline translates it to
  `WHERE n0.node_id = n0.node_id AND n1.node_id = n1.node_id`, a tautology over a cross join of the node table with itself,
  so it ignores both parameters and answers `hops = 1` for any pair. The alternative translates it to `n0.node_id = ? AND
  n1.node_id = ?` and does the lookup. Translation itself costs 34 against 32 microseconds. So the row compares a correct
  lookup with a wrong answer that happens to be cheap; it is listed as slower because it is.
- Two `test_bidirectional_ppr` timing tests (`final-2`: baseline 10 and 30 ms, alternative 20 and 40 ms, in 10 ms steps).
  Cause isolated: the first test's fixture builds the graph, its teardown deletes the rows by SQL, and the second fixture
  builds it again. On the baseline the stored out-degree counters do not follow the SQL delete: after the first fixture the
  sum of `^KG("deg")` over the 1,000 nodes is 4,987 against 4,987 rows; after the teardown it is still 4,987 against 0 rows;
  after the second fixture it is 9,974 against 4,987 rows, wrong on all 1,000 nodes. The baseline's PageRank then divides by
  doubled degrees, returns a different answer (57,556 characters against 56,641 the first time) and finishes in 6 ms. The
  alternative derives degrees from the adjacency, returns 56,641 both times, and takes 11.3 ms. Timed server-side on the
  correct state (the first test), forward PPR is 10.3 ms on the baseline and 11.3 ms on the alternative (1.10); in-IRIS
  over 14 warm runs per side it is 10.7 and 11.3 ms (1.06); the bidirectional call is 29 ms on both. So the alternative is
  level with the baseline when the baseline is correct, and the harness row compares it with the baseline's miscounted state.
  (Probe runs `probe-bidir2`, `probe-bidir8`; the counter audit is `scripts/bench/alt/probes/degree_drift.py`; the parser check is `probes/parser_gc.py`.)
- The first PPR after a burst of writes pays for filling the degree cache: 2.9 to 3.1 microseconds per node cold against 0.5
  warm (of which about 1.6 is the count itself). It is a design cost, measured, not removed; inlining the count did not
  change it (tried and reverted).
- `perf-227-single-graph-latency`: the repo's own gate (scoped search at most 1.1x the legacy scan) fails on both sides, 3 of
  5 on the baseline and 5 of 5 on the alternative, with medians 1.12 and 1.10; the timings themselves are at parity.

### The reader and write kernels (in-IRIS microbenchmark)

The 500,000-edge graph (48,889 sources, one 100,000-edge hub) used throughout this project, five interleaved reps for the
readers and three for the writes. The `*_us_per_edge` rows are microseconds per edge; every other row is microseconds of wall time
for the whole operation (for example `khop_hub_x200` is 200 `KHopCount` calls).

{{MICRO_TABLE}}

Reading it: PageRank 1.05 to 1.09, centrality 1.06 to 1.17, BFS, WCC, `BuildNKG` and `Build2HopStats` at 0.96 to 1.04. A
single `KHopCount` call costs about 0.15 microseconds more (three global reads where the stored counter was one). Centrality
over all sources at 1.17 is the one place a bulk reader is still slower than 10 % (about 0.3 microsecond per node, the extra
list extraction on the warm path). Plain write (1.02) and delete (1.10) are at parity. The keyed rows range from 0.88 to 1.21
with the 50,000-edge keyed write at 1.12, and keyed delete is 1.28 (+0.4 microsecond): slightly slower, plausibly the shared lock
and generation bump in the keyed paths, which I did not isolate.

Where the alternative is faster: the 500,000-edge DRKG load went from 35.3 s of edge loading to 20.1 s (`core-3`), because a
write no longer increments two stored counters; keyed writes are level to faster.

## Breadth beyond the core suites

### Upgrade from 3.x to 4.0.0 (`scripts/bench_migration_4_0_0.py`: 50,000 nodes, 50,000 vectors of 128 dimensions)

{{MIGRATION_TABLE}}

Six interleaved reps with a 20 s settle gap between runs. This was the largest regression found: the first runs
(`migration-1` to `migration-3`) had the alternative at 2.4x to 3.7x the baseline's apply time. The cause was a chain of three
things, each fixed: a shortcut read path in the node-store migration, classes that failed to compile before the graph-scoped
schema existed (leaving a half-compiled class state), and doubled round trips in the backfill. One effect remains: when the two
class versions are deployed alternately into the same scratch namespace in quick succession, an `ALTER TABLE` can wait 10 to
120 s for a lock the other version still holds. That is an artefact of alternating the benchmark, not a cost of upgrading, and
the settle gap removes it. The faster `step.embeddings` and `profile.rekey` rows are plausibly the one-statement backfill used
when a single graph exists; I did not isolate that.

### Caveats that change how these tables should be read

- **Result shape.** IVG's `BFSFastJson` and `NKGAccel.BFSJson` return every edge reached; the Cypher queries return a
  count. The IVG count-style entry points (`KHopCount`) are not in `bench.py`. A comparison of the Q2 to Q4 rows is therefore
  not a like-for-like of the same work. Both IVG entry points are shown; none was chosen.
- **Transport.** Neo4j and Memgraph are queried over Bolt with warm query caches; IVG's ObjectScript entry points are called
  over the Native API in-process on the server, and `execute_cypher` adds translation and SQL.
- **`Q5` at S and M** asks for a path from a node to itself in IVG's recorded run (the pair rule), which Neo4j rejects; its
  distinct-pair variant is in the raw results (`Q5_distinct`).
- **Memgraph algorithms.** Two images were run. The community image has no MAGE: PageRank, betweenness and SCC ran networkx
  inside the server and Louvain, Leiden, closeness and triangles are recorded as skipped. The MAGE image
  (`memgraph/memgraph-mage`) adds native PageRank, betweenness, weakly connected components, a Louvain-style detector and
  Leiden; those rows appear as `memgraph (MAGE)`. MAGE has no closeness or triangle counting, so those two stay skipped.
  Exact betweenness is not attempted above 3,000 nodes on any engine (O(nodes x edges)); on the 100,000-node graph the MAGE
  and community legs run PageRank, WCC and communities only.
- **Noise of the competitor figures.** The networkx control rows (identical code on both IVG sides) differ by 20 % to 28 %
  between runs on this machine, so a competitor ratio under about 1.3 is not a ranking.
- **Published third-party numbers** (GES at SF1000 in `BENCHMARKS.md`) are quoted there as published and were not re-run.
- **LDBC.** Only the KNOWS graph exists on this machine (no datagen, no other SNB files), so only IC2, IC3, IC13 and the
  friend count could run, on the first 10,000 rows (like for like) and, for the competitors only, on all 1.9M rows (in the raw
  results). IVG's full-graph LDBC load was not run.
- **DRKG.** The repository has no DRKG query suite, so the competitor runners' `D_Q1`, `D_Q2`, `D_SP` have no IVG
  counterpart; the only DRKG comparison is loading (IVG 500,000 edges in 20 s on the alternative; Neo4j 5.87M edges in 207 s,
  Memgraph in 65 s; different sizes, the same order of edges per second only for IVG's bulk path against Neo4j's `UNWIND`).

## Not run, and why

- **Full LDBC SNB beyond KNOWS**: there is no datagen output or loader on this machine, only the KNOWS graph. IC2, IC3, IC13 and
  the friend count ran (10,000 rows like for like; 1.9M rows on the competitors only).
- **KGBENCH, the 535M-edge namespace**: it does not exist here and would not fit this machine.
- **Memgraph closeness and triangle counting**: no procedure in either Memgraph image. Exact betweenness above 3,000 nodes on
  any engine, and the Neo4j GDS legs that need it, are skipped for cost.
- **Published third-party numbers** are quoted as published, not re-run.
- Some suites report `tests-failed` on both sides because a timing gate fails under load or an Arno reader walks `USER`; their
  numbers are kept, and the status is in each run's files.
